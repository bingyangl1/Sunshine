# Sunshine 游戏自动化二开 开发规划与排期

> 分支：`feat/automation`
> 目标：基于 Sunshine 开源项目，新增游戏自动化闭环能力，保持与上游官方更新兼容，最小侵入核心代码。

---

## 一、项目概述

### 1.1 核心目标
实现「主机侧画面回传 + 脚本侧智能决策 + 主机侧操作执行」的完整自动化闭环，适用于内网游戏自动化、CV 识别、批量挂机等场景：
- 执行端：游戏运行在主机上，由 Sunshine 负责画面采集、输入模拟
- 决策端：外部 Python/Go 脚本完成图色识别、逻辑决策，通过局域网接口下发操作指令
- 兼容性：原生 Moonlight 客户端连接不受任何影响，自动化功能与原生串流互不干扰

### 1.2 设计原则（长期必须遵守）
1.  **代码隔离**：95% 以上自定义代码放在 `src/automation/` 独立目录，上游核心文件修改量不超过 20 行
2.  **零客户端改造**：初期不修改 Moonlight 客户端，外部脚本作为独立客户端通过 HTTP/WebSocket 与服务端通信
3.  **复用原生能力**：所有输入模拟、视频采集、虚拟 HID、手柄支持直接调用 Sunshine 现有成熟接口，不重复造轮子
4.  **内网安全默认**：所有自动化接口默认仅本地可访问，远程访问需手动开启白名单，默认不暴露公网
5.  **云端编译**：本地零编译环境，所有构建通过 GitHub Actions 完成，push 即出安装包

## 二、整体架构设计

### 2.1 数据流向
```
┌─────────────────────────┐         ┌────────────────────────────┐
│  决策端（你的脚本）      │         │  执行端（Sunshine 服务端）  │
│  Python / Go 脚本       │◄────────►│  47984 HTTPS 自动化接口    │
│  ├─ CV 识别模型         │  HTTP/WS│  ├─ 指令解析层              │
│  ├─ 决策逻辑            │         │  ├─ 输入桥接层（调用原生接口）│
│  └─ 操作序列生成        │         │  └─ 帧回传层                │
└─────────────────────────┘         │           ↓                │
                                    │  原生 Sunshine 核心能力      │
                                    │  ├─ 输入模拟（SendInput/HID/uinput）│
                                    │  ├─ 视频采集（DXGI 等）     │
                                    │  └─ 虚拟 HID 设备          │
                                    └────────────────────────────┘
```

### 2.2 分层设计
| 层级 | 职责 | 位置 |
|------|------|------|
| 接口层 | 对外暴露 HTTP/WebSocket 自动化 API，鉴权、安全校验 | `src/automation/server` |
| 解析层 | 解析外部指令，格式校验、参数合法性检查 | `src/automation/parser` |
| 桥接层 | 将指令转换为 Sunshine 原生输入事件，对接现有输入模块 | `src/automation/bridge` |
| 回传层 | 从视频采集层获取最新帧，按需推送给决策端 | `src/automation/frame_relay` |

### 2.3 端口设计
完全复用 Sunshine 现有端口，不新增任何监听端口：
| 端口 | 协议 | 用途 |
|------|------|------|
| 47984 | TCP HTTPS | 原生 Web 后台 + 自动化接口（路径前缀 `/api/automation/*`） |
| 47998~48002 | UDP | 原生 Moonlight 视频/音频/输入流，完全不改动 |

## 三、任务拆解与排期
总开发周期约 10~13 个工作日，按阶段交付，每阶段完成后可实际验证功能。

### 阶段 1：工程骨架搭建（1 天）
目标：把独立模块目录、挂接点、CI 流程跑通，不写业务逻辑。
| 任务ID | 任务内容 | 验收标准 |
|--------|----------|----------|
| 1.1 | 创建 `src/automation/` 目录骨架，编写 CMakeLists 编译规则 | 目录代码能被 CI 正常编译，不影响原有构建 |
| 1.2 | 在 `main.cpp` 加最小挂接点：启动时初始化 automation 服务，退出时销毁 | 程序启动不报错，自动化服务在本地 47984 端口正常监听 |
| 1.3 | 验证 CI 编译流程：push 后 GitHub Actions 能正常出 ZIP 安装包 | Actions 任务成功，下载安装包可正常启动 Sunshine |
| 1.4 | 配置基础鉴权：自动化接口复用 Web 后台 Token 校验，无 Token 请求返回 401 | 未带 Token 请求被拒绝，带合法 Token 可访问 |

**交付物**：可正常安装、带空 automation 模块的基础版本。

---

### 阶段 2：核心闭环 MVP（3~4 天）
目标：跑通最基础的「发指令控输入、拉画面帧」闭环。
| 任务ID | 任务内容 | 验收标准 |
|--------|----------|----------|
| 2.1 | 实现绝对鼠标控制接口：`POST /api/automation/mouse/move_abs`（x/y 坐标） | 脚本发指令，鼠标能准确移动到指定屏幕位置 |
| 2.2 | 实现鼠标按键接口：左键/右键/中键按下/释放 | 能模拟点击，点击位置准确，无偏移 |
| 2.3 | 实现鼠标滚轮接口：上下滚动 | 滚轮滚动幅度与指令参数一致 |
| 2.4 | 实现键盘控制接口：按键按下/释放，支持全键盘码表 | 模拟按键能被游戏识别，无按键错乱 |
| 2.5 | 实现相对鼠标控制接口：`POST /api/automation/mouse/move_rel`（dx/dy 偏移） | 相对移动幅度准确，FPS 游戏内鼠标位移正常 |
| 2.6 | 实现单帧拉取接口：`GET /api/automation/frame` 返回最新 JPG 截图 | 脚本拉取的画面与实际游戏画面一致，延迟 <50ms（局域网） |
| 2.7 | 封装 Python SDK：3~5 行代码完成连接、发指令、拉帧 | 示例脚本可直接运行，控制鼠标移动、拉截图 |

**交付物**：MVP 版本 + Python 调用示例，完成最基础自动化流程。

---

### 阶段 3：生产稳定性优化（3~4 天）
目标：保证 7×24 小时连续运行，解决长期使用中的稳定性问题。
| 任务ID | 任务内容 | 验收标准 |
|--------|----------|----------|
| 3.1 | 输入状态机校验：按键按下/释放配对，网络丢包自动补发，杜绝卡键 | 连续高频发指令 1 小时无按键卡死问题 |
| 3.2 | 全局紧急停止接口：`POST /api/automation/emergency_stop` 清空所有按下的按键/鼠标状态 | 执行后所有输入状态复位，游戏角色停止移动 |
| 3.3 | 鼠标指令合并：连续移动指令自动合并，减少网络小包数量 | 高频移动场景下 CPU 占用无明显升高 |
| 3.4 | WebSocket 连续帧推送：支持按需设置帧率、分辨率缩放 | 脚本可通过 WS 实时接收 15/30/60fps 画面，带宽占用可控 |
| 3.5 | 帧时间戳标记：每帧附带主机时间戳，支持延迟计算 | 可计算出端到端网络延迟，支持操作补偿 |
| 3.6 | 人机协同保护：检测到真实 Moonlight 客户端连接时自动暂停自动化输入 | 有人远程接入时，自动化指令不抢占鼠标 |
| 3.7 | 日志系统：所有自动化操作、错误写入日志文件，方便排查 | 日志可追溯每一条指令的执行结果、异常原因 |
| 3.8 | 配置项集成：所有自动化参数（监听白名单、默认帧率）写入原生配置文件 | Web 后台可修改自动化相关配置，无需改代码 |

**交付物**：稳定版，可连续运行 24 小时无崩溃、无内存泄漏、无卡键。

---

### 阶段 4：高级能力拓展（按需迭代）
目标：覆盖更复杂的游戏场景，不强制一次性完成。
| 任务ID | 任务内容 | 优先级 |
|--------|----------|--------|
| 4.1 | 虚拟手柄控制：复用原生 ViGEm 能力，支持摇杆、按键、扳机指令 | 高 |
| 4.2 | 多屏坐标适配：虚拟显示器场景下自动做坐标映射 | 中 |
| 4.3 | 批量指令序列：支持一次发送带时间间隔的操作序列，减少网络往返 | 中 |
| 4.4 | 事件主动推送：画面变化、弹窗出现等事件主动推送给脚本 | 低 |
| 4.5 | 输入模式切换：根据游戏兼容性自动切换 SendInput/虚拟 HID 模式 | 低 |

## 四、代码规范与目录结构
### 4.1 自定义代码目录
```
src/automation/
├── automation_server.h/cpp    # HTTP/WebSocket 服务主类
├── command_parser.h/cpp       # 指令解析、参数校验
```

### 4.2 上游文件修改清单（严格控制修改量）
| 文件 | 修改内容 | 累计代码量 |
|------|----------|-----------|

| `src/input.h/cpp` | 暴露输入接口供 bridge 调用 | <10 行 |
| `src/video.cpp` | 1 行帧回调注册 | <3 行 |
| **合计** | | **<30 行** |

### 4.3 代码规范
严格遵循仓库根目录 `.clang-format` 格式规范，所有公开类、函数补充完整 Doxygen 注释，新增接口配套 gtest 单元测试。

## 五、分支与 CI 流程
1.  **分支规范**：
    - `main` 分支：完全同步上游官方代码，不做任何修改
    - `feat/automation` 分支：所有自定义二开代码的开发分支
2.  **CI 流程**：
    - push 到 `feat/automation` 分支自动触发 Windows x64 编译
    - 编译完成后在 Actions 页面下载 ZIP 安装包，本地解压即可使用
3.  **上游同步流程**：
    - 上游发新版时，先拉取 upstream 到 `main` 分支
    - 将 `main` 合并到 `feat/automation`，仅需手动确认上述 4 个挂接点的代码位置，5 分钟即可完成同步

---

## 六、长期维护保障
1.  所有自定义代码隔离在独立目录，上游更新不会产生大面积冲突
2.  每次合并上游更新后，自动运行核心功能冒烟测试（鼠标控制、帧拉取），保证核心能力不被破坏
3.  接口保持向后兼容，外部脚本不需要随版本升级修改调用逻辑
